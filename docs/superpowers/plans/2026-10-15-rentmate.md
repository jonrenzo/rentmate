# Rentmate Implementation Plan

> **For agentic workers:** Use the subagent-driven-development and dispatching-parallel-agents skills for the independent backend and domain tasks. The primary agent implements and integrates the interface.

**Goal:** Build the approved rent-management app, including a usable local demo and deployable Supabase-backed version.

**Architecture:** One Next.js app serves an owner dashboard and renter PWA. React consumes the AppState/Action contract in `lib/types.ts`. Live data stays behind authenticated route handlers and Supabase RLS; the local demo exercises equivalent business rules on synthetic browser-local data.

**Tech Stack:** Next.js, React, TypeScript, Supabase, Lucide React, Satoshi. Node test runner with tsx; PostgreSQL tests where feasible.

**Spec:** `docs/superpowers/specs/2026-10-15-rentmate-design.md`

## Global constraints

- Full month payments, individual bills, generation 3 days before due date, Asia/Manila dates, PHP centavos.
- Single owner, assigned usernames, forced temporary-password change, former renters read-only.
- No electricity/late fees/exports/offline private data/paid integrations. Preserve approved Satoshi + Lucide light design.
- Do not modify the existing ERP Supabase project. Demo must be explicitly separate from live data.

## Tasks

1. **Foundation and shared contract** (`lib/types.ts`, package/config, app shell): pin dependencies, define records/actions, save spec. Check TypeScript and development server.
2. **Domain and local demo** (`lib/domain.ts`, `lib/demo.ts`, `tests/domain.test.ts`): write failing tests for date clamping, bill visibility, amount/role checks, payments and held funds; implement pure functions and demo reducer. No auth/security claims for demo. Tests must pass with real state transitions.
3. **Supabase backend** (`lib/server/*`, `app/api/*`, `supabase/*`, `scripts/*`): implement secure sessions, account/reset/password flows, state loading, actions, uploads and signed URLs. Atomic SQL money functions and idempotent cron billing. Test RLS, duplicate operations and tampered ownership. Document setup and recovery.
4. **Interface and PWA** (`components/*`, `app/*`, `public/*`): approved dashboard/renter style, functional rooms/renters/forms/bills/payment review/settings/account/move-out. Loading/error/empty/pending states, focus/keyboard support, full amounts, connectivity handling, manifest/icons and network-only private requests. Integrate same contract with demo/live API adapters.
5. **Integration and review**: production build, typecheck, test suite, dependency audit, browser interaction at desktop and phone sizes. Fresh review of security/business logic, fix significant findings, then open working app and report setup limits honestly.

## Review focus

- A renter or temporary-password account must not bypass UI restrictions by calling APIs or Supabase directly.
- Concurrent proofs, approvals and cash/deposit settlement must not count a bill twice.
- Month-end due days and missed cron runs must not skip or duplicate bills.
- Former renters retain access to their records without creating new payment or occupancy mutations.
- Failed account creation, image upload, or money operation must not leave misleading balances or exposed images.
